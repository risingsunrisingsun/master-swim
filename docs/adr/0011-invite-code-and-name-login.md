# ADR-0011: 초대코드로 가입하고 이름과 비밀번호로 들어온다

- 상태: 채택
- 날짜: 2026-10-07
- 근거: PRD-0001 §4.0

## 맥락

회원제 카페 회원만 들어와야 한다. 네이버 카페 가입 여부는 API 로 확인할 수 없으므로
명단은 운영자가 직접 관리한다. 회원에게 이메일·전화번호를 받지 않기로 했다.

Supabase Auth 는 이메일이나 전화번호를 식별자로 요구한다.

## 결정

1. **운영자가 회원을 먼저 만든다** (`members` 행: 표시명, 역할). 표시명은 유일하다 —
   동명이인은 운영자가 `김민수A` 처럼 구분한다.
2. 운영자가 그 회원의 **초대코드**를 발급한다. 8자, 헷갈리는 글자(0·O·1·I·L) 없음,
   7일 유효, 1회용. DB 에는 **SHA-256 해시만** 둔다 — 화면에 한 번 보이고 끝이다.
3. 회원은 초대코드와 새 비밀번호를 넣는다. Edge Function `redeem-invite` 가
   service_role 로 Auth 사용자를 만들고 `members.user_id` 에 잇는다.
   Auth 이메일은 **`<members.id>@` + 내부 도메인**이다. 실제로 보내지 않는 주소이고
   회원은 이 값을 볼 일이 없다. 표시명이 바뀌어도 로그인이 깨지지 않도록 이름이 아니라
   id 로 만든다.
4. 로그인은 **표시명 + 비밀번호.** 앱이 RPC `login_email(표시명)` 으로 내부 이메일을 받아
   `signInWithPassword` 를 부른다.
5. **비밀번호 분실 = 초대코드 재발급.** 이미 가입한 회원의 코드를 쓰면 같은 함수가
   새 비밀번호로 바꾼다. 흐름이 하나라 운영자가 익힐 것도 하나다.

### 보완 (2026-10-08) — 운영자가 비밀번호를 정해 준다

처음 운영을 시작할 때 운영자가 명단을 일괄 입력하면서 **초기 비밀번호를 직접 정한다**.
30명에게 초대코드를 하나씩 보내고 가입을 기다리는 것보다 빠르다.

- Edge Function `set-passwords` 가 활성 운영자인지 확인하고, 가입 전 회원은 Auth 사용자를
  바로 만들고, 가입한 회원은 비밀번호를 바꾼다. 남은 초대코드는 무효로 한다.
- Auth 사용자 메타데이터에 `temp_password` 를 켠다. 회원 홈에 "비밀번호를 바꿔 주세요"가 뜨고,
  **내 계정**에서 스스로 바꾸면 꺼진다. 운영자가 회원 비밀번호를 아는 상태를 오래 두지 않기 위해서다.
- 로그인한 회원 · 운영자는 **내 계정**에서 지금 비밀번호를 확인받고 스스로 바꾼다.
- 초대코드 흐름은 그대로 남는다. 비밀번호를 비워 두면 초대코드가 나간다.

## 결과

- `login_email` 은 익명으로 부를 수 있으므로 "그 이름의 회원이 있다"는 사실이 드러난다.
  로그인 실패 문구로도 어차피 드러나는 정보이고, 30명 동호회에서 명단은 비밀이 아니다.
- **PRD 의 "5회 실패 시 15분 잠금"은 직접 구현하지 않는다.** Supabase Auth 의 IP 단위
  요청 제한에 맡긴다. 회원별 잠금은 실패 횟수를 서버에 따로 세야 하는데, 그러면 누구든
  남의 이름으로 다섯 번 틀려서 그 회원을 잠글 수 있다.
- Supabase 대시보드에서 **이메일 확인(Confirm email)을 끈다.** 내부 주소로는 메일이
  가지 않는다.
- 첫 운영자는 앱으로 만들 수 없다. SQL 편집기에서 `members` 에 `role = 'admin'` 행을 넣고
  `issue_invite` 를 부른다 (`app/supabase/README.md`).
